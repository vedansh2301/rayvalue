### Task 3: Calculator engine (SPEC Phase 3)

Pure TypeScript in `src/lib/calc/` — no DOM, no fetch, no imports from Astro. Inputs are passed in explicitly (utility record, costs, assumptions, production data) so functions stay pure; a thin `calculate()` orchestrator composes them.

Modules (suggested):
- `types.ts`: `Range = { low: number; likely: number; high: number }`, `CalcInput = { zip, utilityId, avgMonthlyBill, battery: 0|1|2, shading: 'none'|'some'|'heavy' }`, `CalcResult` (either `{ ok: true, size: Range (kW), cost: Range ($), year1Savings: Range ($), paybackYears: Range (number | null meaning "> 25 yrs/never"), netSavings25: Range, annualUsageKwh, assumptions: string[], warnings: string[] }` or `{ ok: false, reason: 'invalid_zip' | 'unknown_utility' | 'state_mismatch' | 'missing_data' | 'invalid_bill', missing?: string[] }`).
- `usage.ts`: `estimateAnnualKwh(monthlyBill, utility)` — subtract fixed_monthly_charge; tiered: invert the tier schedule (fill tier 1 kWh until its cost is exhausted, then tier 2…); tou_summary: divide by effective rate. Bill ≤ fixed charge → 0 usage (then result warns). Returns annual kWh (×12).
- `production.ts`: shading → PVWatts `losses` % from assumptions; `kwhPerKwYear` comes from the caller (Task 4 provides it from PVWatts at the losses value; Task 3 takes it as an input `productionKwhPerKw: { none|some|heavy?...}` or simply a number already for the chosen losses). Keep the interface: `calculate(input, { utility, costs, assumptions, kwhPerKwYear })`.
- `sizing.ts`: kW = annualKwh × offset ÷ kwhPerKwYear; low/likely/high from offset range (0.90 / 0.95 / 1.00); cap at size cap (add warning when capped); minimum sensible size (e.g. 2 kW) — if usage implies less, warn "bill may be too small for solar to make sense".
- `cost.ts`: cost range = kW × 1000 × $/W range (low size × low $/W … high × high) + battery count × battery cost range. Federal credit applied = 0, and the assumptions list states "No federal tax credit (25D ended for 2026+ installs)".
- `savings.ts`:
  - FL retail net metering: year-1 savings = bill reduction computed by re-pricing remaining kWh through the tiers (cost(usage) − cost(max(0, usage − production))). Fixed charge is never offset. Batteries in FL add cost but no bill savings under retail net metering (state this in assumptions: backup value only).
  - CA NEM 3.0 net billing: production split into self-consumed (share from assumptions by battery count) × retail effective rate + exported × avg_export_credit_per_kwh, with self-consumed kWh capped at usage.
- `payback.ts`: year-by-year cash flow over analysis years with rate escalation and panel degradation; payback = first year cumulative savings ≥ cost (linear interpolation within the year, round to 0.5); null if never within 25 years. 25-year net savings = cumulative savings − cost. Range composition: "low" outcome = high cost + low savings + low escalation; "high" = low cost + high savings + high escalation; "likely" = likely everything. Payback low/likely/high ordered so `low` = best (shortest) — document the ordering clearly in types and assumptions.
- Missing data: if any needed value is null → `{ ok: false, reason: 'missing_data', missing: [paths] }`. Never substitute made-up defaults.
- `assumptions` array: human-readable strings built from the actual values used (e.g. "Installed cost $X–$Y per watt (source: …)").
- Rounding happens in a `round.ts` helper applied to output (kW 0.1, $ nearest 100, years 0.5).

Tests (`src/lib/calc/*.test.ts`): use **synthetic test fixtures** (not the real data JSON, which may be null) with hand-calculated expected values worked out in comments: one FL tiered fixture (two tiers), one CA tou_summary fixture, for each: usage estimate, size, cost, year-1 savings, payback. Plus an integration test per real utility id that either computes successfully or returns `missing_data` listing exactly the null fields. Edge cases: tiny bill (≤ fixed charge), huge bill (hits cap), invalid ZIP (non-numeric, 4 digits, out-of-state ZIP like 10001), utility/state mismatch (FL ZIP + PG&E), missing data, battery 0/1/2, shading none/some/heavy monotonic (more shade → bigger system for same offset or lower production → lower savings).

Done when tests pass with hand-checked fixtures. Commit.
